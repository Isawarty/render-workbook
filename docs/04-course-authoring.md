# 课程任务编写、调试反馈与最小检查点规范

本文是 `render-workbook` 的课程编写规范，约束现有项目改造和 P3 之后的新内容。
目标学习者是有较强编程基础、能够主动使用调试器、validation layer、日志和 GPU 调试工具的
高水平自学者。课程的目标不是让学习者沿着细碎测试逐格通关，而是训练其独立构建、观察和
调试真实 Vulkan / 图形学系统的能力。

因此，本规范不把 SLOC 多或挖空率高直接视为问题，也不要求把 P1 改成 API 填空题。
P1 从 instance 写到多帧同步的完整实现量具有学习价值。课程改造的重点是保证故障可观察、
最终验收可信，并只在普通调试手段难以跨越的语义边界设置少量 checkpoint。

## 1. 规范用语与范围

- **必须**：不满足就不能发布新的 `start/*` / `done/*` tag。
- **应当**：默认遵守；偏离时在任务书中说明原因。
- **可以**：按题目特点选择。

本文中的 **task** 指 `pXX-tYY`，对应一次完整概念交付和一组 `start/done` tag。
**checkpoint** 是 task 内可单独运行的局部诊断入口，不是必经关卡，不创建新分支或 tag。

本规范从 P3 及后续内容开始作为发布门槛。P1/P2 是在它之前完成的，**不回头改造** ——
它们现有的 validation、日志和任务级测试已经够用，为了对齐规范去重建一条已经逐 tag
验证过的提交链，代价远大于收益。

**目前仓库里一个 checkpoint 也没有。** `pXX-tNN-cpNN` 只是预留下来的命名约定和运行
接口（`rwb.py` 已经能解析），等到 P3 真的撞上第 2.3 节那种不可观测的故障边界时再用。
在此之前不要宣称任何 tag 含有 checkpoint。

## 2. 教学原则

### 2.1 保留真实实现与完整故障链

- 必须保留形成完整心智模型所需的实现责任。Vulkan 初始化、资源生命周期、同步和状态转换，
  不得因为代码长就整体下放给框架。
- SLOC 和挖空率只用于估计工作量，不用于决定 task 是否必须拆分。
- 调试本身是学习成果。只要错误可观察、可复现且有合理定位入口，允许学习者面对较长的故障链。
- 框架只接管已经学过、与当前概念无关或会让骨架无法安全运行的工作。
- 每个 task 必须写明学习者最终获得的能力，而不只是列出 API。

### 2.2 可观测性优先于 checkpoint

增加 checkpoint 前，应当先检查以下反馈面是否已经足够：

- 编译器、链接器和 `RWB_TODO` 能否准确定位未完成接口；
- validation layer（含 sync validation）能否报告违反的 Vulkan 规则；
- 日志是否给出所选设备、queue family、format、extent、image count 等关键决策；
- Vulkan 对象是否设置 debug name / label，便于 RenderDoc、Nsight Graphics 或 validation 消息定位；
- hang、device lost、swapchain 重建等路径是否有超时、阶段日志或最近提交信息；
- 最终测试失败时，是否能区分 validation、结构回读和图像结果三类问题。

若这些手段足以让目标学习者建立并验证自己的假设，就不应为了“更快变绿”增加 checkpoint。
checkpoint 不能替代阅读 validation、设置断点、抓帧和检查状态转换。

### 2.3 checkpoint 的准入条件

只有满足下列至少一项时，才应新增 checkpoint：

1. 错误跨越异步 CPU/GPU 边界，最终症状主要是 hang、device lost 或无输出；
2. 多个独立子系统会坍缩为同一症状，常规日志、validation 和抓帧仍难以区分；
3. 中间状态不可直接观察，且错误会被后续步骤覆盖或破坏；
4. 硬件或驱动差异使最终像素结果不足以证明规范不变量；
5. 存在适合单独验证的纯 CPU 边界，能避免把解析错误和 GPU 集成错误混在一起。

以下情况本身不足以增加 checkpoint：

- 参考实现 SLOC 高、函数长或 Vulkan 结构体字段多；
- task 同时引入多个相关 API；
- 完成时间超过某个固定分钟数；
- 学习者需要主动使用调试器、RenderDoc 或规范文档。

默认每个 task 为 **0–1 个 checkpoint**。两个 checkpoint 已属于高复杂度任务；三个及以上必须在
任务书中逐项说明不可观测的故障边界，并由课程维护者复核。数量越多不代表教学质量越高。

### 2.4 checkpoint 不得成为答案预言机

- 只验证一个稳定的语义边界或规范不变量，不逐字段复刻参考实现。
- 允许不同的合法算法、helper 划分、资源组织和控制流。
- 不为测试暴露不合理的 public 成员；内部决策优先通过纯函数、窄 `TestAccess` friend 或只读
  调试快照观察。
- checkpoint 的失败信息可以指出被破坏的不变量和观测位置，但不应给出完整调用序列或字段表。
- 学习者可以跳过 checkpoint 直接运行 final；除安全保护外，checkpoint 不构成解锁条件。

## 3. 反馈工具箱

下面是可选反馈机制，不是每题都要走完的等级阶梯。

| 机制 | 适合回答的问题 | 典型实现 |
|---|---|---|
| 构建反馈 | 接口、类型和依赖是否接通 | 编译、链接、`RWB_TODO` 定位 |
| 纯逻辑测试 | 选择、计算和解析是否正确 | 表驱动测试、性质测试、最小资产 |
| 状态快照 | 资源和决策是否符合不变量 | 只读摘要、句柄/数量/flags/layout 日志 |
| 运行诊断 | 调用链和同步是否合法 | validation、短帧运行、超时保护、GPU labels |
| 最终验收 | 完整能力是否成立 | L1 validation、L2 readback、L3 golden |

使用原则：

- 优先把诊断能力放进 final 的失败输出，而不是复制成多个 checkpoint。
- L3 只能证明最终图像接近预期，不能单独证明 queue、barrier、layout 或 descriptor 正确。
- 涉及跨 GPU 差异的行为，优先验证规范不变量，像素结果只作补充。
- 必做路径不得因缺少 golden、设备能力不足或资产未触发而静默 `SKIP`；合法降级必须有替代断言。

## 4. 运行接口与任务书

最终验收沿用稳定名称：

```bash
python rwb.py test p01-t02
```

确有必要的 checkpoint 使用两位编号：

```text
p01-t02-cp01
p01-t02-cp02
```

```bash
python rwb.py test p01-t02-cp01
```

Catch2 标签同时保留 task 和 checkpoint，例如 `[t02][cp01]`。checkpoint 不增加 Git 标签；
工作流仍是 `start/p01-t02`、`done/p01-t02` 和学习者自己的 `mine/p01-t02`，中间状态用普通
commit 保存。

每份任务书必须包含“调试入口”小节，至少说明：

- final 命令和通过信号；
- 建议开启的 validation / 日志；
- 关键可观测状态或推荐断点位置；
- 常见失败属于 CPU 逻辑、Vulkan 状态还是输出差异；
- 何时值得抓帧或打开同步验证。

只有存在 checkpoint 时才增加下表，不为了形式写空表：

| checkpoint | 验证的不可观测边界 | 运行命令 | 通过信号 | 仍需自行调试的部分 |
|---|---|---|---|---|
| cp01 | 一个明确语义边界 | 精确命令 | 可观察不变量 | 不泄露后续实现 |
| final | 完整 task | 精确命令 | L1/L2/L3 组合 | 综合诊断入口 |

失败消息应包含被破坏的不变量，以及能取得时的实际值和期望值。它可以给出下一处观测位置，
但不应变成逐步解题脚本。

## 5. 提示分层

本项目用于自学，详细文档是资产，但学习者应能控制提示暴露程度：

- **任务正文**：概念、接口契约、验收标准和设计动机；
- **Hint 1**：规范章节、相关对象和关键不变量；
- **Hint 2**：状态图、数据流或调用顺序；
- **Hint 3**：接近伪代码的字段清单和常见正确组合；
- **参考实现**：通过 `done/*` diff 主动查看。

内联 TODO 优先保留契约和安全条件，完整步骤放进任务书的分层提示。P1 现有详细说明可以保留，
但新增提示应避免把调试推理提前替学习者做完。

## 6. 测试与资产规范

### 6.1 测试覆盖

- 每项必做能力必须由 final 或必要 checkpoint 验证；不要求每个 TODO 对应一个独立测试。
- 多个 TODO 可以共同形成一个系统级验收，只要失败仍可通过既有诊断面定位。
- 测试覆盖任务书声称“必须支持”的行为；未覆盖行为明确标为扩展练习。
- 公共测试必须支持自学诊断，但不得过度规定内部实现结构。
- 资源、同步和生命周期题的 final 必须运行 L1 validation；适合回读的结果优先增加 L2。

### 6.2 资产触发真实路径

如果任务书要求支持输入变体，至少一个测试资产必须真正包含它。例如 glTF 任务若要求
`byteStride`、node rotation、不同 index 类型、缺失可选属性或父子变换，就必须提供相应的
最小资产或生成器测试。没有资产覆盖的能力应降级为扩展练习。

## 7. 发布门槛

新增或改造 task 在发布 tag 前必须满足：

1. `start/*` 骨架可编译，并能清楚指出首个未实现入口；
2. 学习者可以不运行 checkpoint，直接调试并完成 final；
3. `done/*` 上 final 和所有已注册 checkpoint 全绿；
4. final 有足够的 validation、日志或状态摘要来区分主要故障类别；
5. 必做测试无静默 skip，后续 tag 保持判分单调性；
6. 任务书命令与真实 CTest 名称一致；
7. 至少人工注入一个常见错误，确认失败信号能指向正确概念；
8. 每个 checkpoint 都有第 2.3 节所述的准入理由。

`.authoring/verify-grading.py` 后续应检查 task 单调性、命令一致性和必做测试无 skip；只有实际
存在 checkpoint 的 task 才检查其可独立运行性。

## 8. 质量指标

| 指标 | 用途 | 是否发布门槛 |
|---|---|---|
| solution-added SLOC / 局部挖空率 | 估计实现工作量 | 否 |
| checkpoint 数 | 监控是否过度脚手架化 | 否；默认越少越好 |
| 不可观测故障边界覆盖率 | 决定是否需要 checkpoint 或诊断增强 | 是，必须覆盖或说明 |
| final 诊断面完整性 | 确保能区分主要故障类别 | 是 |
| 必做能力的断言/资产覆盖率 | 防止“要求了但测不到” | 是，100% |
| 必做测试 skip 数 | 防止假绿 | 是，必须为 0 |
| checkpoint 可绕过性 | 保留独立调试和系统推理训练 | 是 |

当前审计数据只作基线：P1 task 文件加权挖空率约 85.8%，P2 约 79.2%；项目源码范围内学生
实现占比分别约 51.8% 和 36.1%。这些数字说明 P1 实现责任更完整，**不构成改动理由**。
新 task 做得好不好，看 final 的可诊断性、不可观测边界覆盖和测试真实性，
不看 checkpoint 数量，也不看挖空率。

## 9. 新 task 编写清单

- [ ] 写清最终能力、非目标和学习者负责的真实实现。
- [ ] 提供 final 命令、通过信号和“调试入口”小节。
- [ ] 为关键 Vulkan 对象补充 debug name、阶段日志或只读状态摘要。
- [ ] 开启适用的 validation / sync validation，并区分 validation、回读和图像失败。
- [ ] 逐项审查不可观测故障边界；能用调试面解决时不新增 checkpoint。
- [ ] 如需 checkpoint，记录第 2.3 节准入理由，并保持可绕过、非答案预言机。
- [ ] 文档必做输入分支都有断言或最小资产，否则降为扩展练习。
- [ ] 骨架编译、必做测试无 skip、`done/*` 全绿且后续 tag 单调。
- [ ] 人工注入常见错误，验证 final 的诊断质量；失败后再决定是否补 checkpoint。
- [ ] 保持现有 `start/done/mine` Git 工作流，不为 checkpoint 增加 tag。
